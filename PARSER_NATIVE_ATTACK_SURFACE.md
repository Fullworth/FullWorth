# Parser native-library attack surface\n\n## Threat model\n\nUploaded statements are untrusted. A malformed PDF or image can target managed parsers, image decoders, Leptonica, Tesseract, language-model data, or the process boundary around those components. FullWorth therefore treats successful file signature and size validation as admission control, not as proof that parser input is safe.\n\nThe security objective is containment: parser compromise or pathological input must have bounded CPU, memory, process, file-descriptor, temporary-storage, network, and persistence impact. Repository and CI evidence cannot prove that an exact production release is deployed or that a host kernel contains an unknown native exploit.\n\n## Native components\n\nThe production parser image contains the .NET runtime, PdfPig and managed application dependencies from the published worker, Debian's `libtesseract5`, its Leptonica dependency, the English `tesseract-ocr-eng` trained model, and the minimum runtime packages required for TLS and cgroup bootstrap. The external image is digest-pinned, and release SBOM/provenance workflows inventory the resulting image rather than assuming that the base digest alone freezes Debian package resolution.\n\nThe API never loads Tesseract or Leptonica. It sends admitted document bytes to the dedicated parser worker over authenticated internal TLS. Native OCR executes only inside a per-image cgroup nested beside the per-document cgroup.\n\n## Enforced boundary\n\nThe production parser worker has all of these independent controls:\n\n- one internal-only Docker network shared only with the API, with no host port publication;\n- a read-only root filesystem and a private 64 MiB `/tmp` tmpfs mounted `noexec,nosuid,nodev`;\n- a minimal init to reap abandoned native children;\n- core dumps disabled and a 512-descriptor hard/soft ceiling;\n- a 64-process container ceiling, finite container CPU and 512 MiB memory ceilings, and no additional swap;\n- `no-new-privileges`, all capabilities dropped for the running UID 1654 supervisor, and an empty effective and bounding capability set;\n- only the temporary bootstrap capabilities needed to create delegated cgroups and drop identity;\n- disabled .NET diagnostics and no interactive health-exec process injected into the delegated cgroup parent;\n- authenticated TLS requests with timestamp, nonce, body hash, and HMAC validation;\n- application limits for request bytes, PDF pages, extracted characters, images per page, per-image bytes and pixels, and cumulative declared image pixels;\n- per-document cgroups with one CPU quota, 384 MiB memory, zero swap, and 48 PIDs;\n- stricter per-image sibling cgroups around native image decode/OCR, with the same CPU and 384 MiB memory ceilings;\n- cgroup removal after each scope, plus fail-closed behavior when the required cgroup-v2 controllers cannot be established.\n\nThe writable cgroup mount is intentionally confined to the parser container because the worker must create child limits. Root is present only for deterministic bootstrap; the entrypoint then moves the worker into a leaf cgroup, drops to UID/GID 1654, and removes all capabilities from both effective and bounding sets before serving requests.\n\n## Verification\n\n`deploy/tests/parser-native-boundary-tests.sh` regression-locks the declared image, Compose, verifier, and documentation boundary before container startup.\n\nThe Linux production-container job builds the exact parser image, verifies its release revision and SBOM/provenance inputs, starts the full production Compose topology, and observes live per-document and per-image cgroups during synthetic OCR. It checks finite CPU/memory/PID/swap values, UID 1654, empty capability sets, read-only and no-port topology, init, ulimits, disabled diagnostics, cgroup cleanup, and continued readiness.\n\nThe containment self-test deliberately exceeds the child memory ceiling and requires a kernel OOM-kill counter increase while the supervisor survives. Logs are then checked to ensure neither the synthetic document marker, parser credential, nor native-library diagnostics appeared.\n\n## Residual risk\n\nNative-library vulnerabilities remain possible. A container and cgroup boundary reduce blast radius but are not a substitute for prompt base-image rebuilds, dependency scanning, kernel/container-runtime patching, or production monitoring. The parser currently shares the host kernel and intentionally receives writable access to its own cgroup hierarchy. A kernel escape, cgroup delegation defect, compromised Docker daemon, or host compromise is outside this repository-only proof.\n\nThe current one-worker topology also bounds rather than eliminates denial of service: repeated admitted documents can consume the worker's finite budget. Existing request rate limits and queue behavior provide upstream pressure, while a future multi-worker design would require a new aggregate resource and concurrency review.\n\n## Change procedure\n\nAny change to parser packages, Dockerfile stages, Compose capabilities, cgroup code, request authentication, document limits, network attachments, writable mounts, diagnostics, or production CI must update this review and its regression contract. Acceptance requires both required checks green for the exact PR head. Deployment and production acceptance require separate evidence from the guarded exact release on the target host.\n
