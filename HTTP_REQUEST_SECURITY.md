# HTTP request framing and media-type security

FullWorth uses two parsing boundaries before application code handles a public
request:

1. Caddy terminates the public TLS/HTTP connection and creates the upstream
   request.
2. Kestrel parses the internal request for the API or Web host.

Application middleware does not attempt to reinterpret raw HTTP framing. That
belongs to the protocol servers, before ASP.NET Core exposes an
`HttpRequest`.

## Framing ambiguity

The production HTTP security verifier sends raw HTTP/1.1 requests through the
real public edge and verifies two complementary defenses:

- a request containing both `Transfer-Encoding: chunked` and a deliberately
  conflicting `Content-Length` is canonicalized to the complete chunked body.
  The probe sends a valid logout JSON document whose declared length is only one
  byte and requires HTTP 204 plus `X-FullWorth-Request-Id`, proving Caddy and
  Kestrel agree on the chunked message boundary; and
- a request containing conflicting `Content-Length` values is rejected with
  HTTP 400 before it reaches the API.

The rejected duplicate-length response must omit
`X-FullWorth-Request-Id`. That header is generated by the API, so its absence
proves the invalid frame stopped before application middleware or endpoint code.
A failed framing probe fails the production-container CI gate and the guarded
deployment acceptance script.

Kestrel additionally retains explicit limits of 8 KiB for the request line,
32 KiB for aggregate request headers, and 1 MiB for ordinary request bodies.
Statement uploads retain their separately reviewed 16 MiB request and 15 MiB
file limits.

## Content types

For body-bearing POST, PUT, PATCH, and DELETE requests on application-owned
surfaces, FullWorth accepts only the media-type families the product uses:

- `application/json` and `application/*+json`;
- `application/x-www-form-urlencoded`; and
- `multipart/form-data`.

The API applies this boundary to `/api`. The Web host applies it to `/auth`
and `/bff`. Missing or unsupported media types receive HTTP 415 before
authentication, antiforgery body processing, model binding, provider calls,
proxy work, or endpoint execution. Bodyless mutation requests remain valid
without a content type.

This allowlist is a first boundary, not a substitute for endpoint-specific
format checks. JSON model binding, HTML form endpoints, multipart statement
validation, file signature checks, and the Stripe webhook's JSON-only rule
continue to enforce their narrower contracts.

## Verification boundary

Integration tests cover missing and unsupported media types, JSON and
`+json` acceptance, HTML form acceptance, and bodyless POST behavior. The
production-stack verifier covers ambiguous HTTP/1.1 frames against Caddy.

These checks establish repository and production-like stack behavior. They do
not claim that a feature-branch build is deployed or that an external network
path has been observed. Production acceptance still requires the guarded release
workflow and evidence from the exact deployed release.
