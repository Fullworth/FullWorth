# Security event telemetry

FullWorth emits a dedicated structured log category, `FullWorth.SecurityEvents`, for request-boundary security outcomes and a separate `FullWorth.SecurityAlerts` category for bounded repeated-event alerts.

## Events

| Event ID | Name | Trigger |
| --- | --- | --- |
| 29001 | `authentication_rejected` | HTTP 401 |
| 29002 | `authorization_denied` | HTTP 403 |
| 29003 | `rate_limit_rejected` | HTTP 429 |
| 29004 | `ownership_scoped_resource_not_found` | An authenticated request receives 404 on one fixed allowlisted ownership-scoped method/route template |
| 29011 | `admin_mutation_completed` | A persisted staff-role, entitlement, program-membership, or subscription-access-key mutation completes |
| 29012 | `account_export_completed` | A strongly reauthenticated account export is successfully constructed |
| 29013 | `account_deletion_completed` | Account deletion commits successfully, including the accepted-cleanup-pending case |
| 29014 | `financial_provider_attention_required` | An owned active Plaid connection is successfully persisted to `RequiresAttention` after a user-action-required sync error |

The middleware surrounds rate limiting, authorization, and endpoint execution, so rejected requests are observed even when a downstream component short-circuits the pipeline.

## Allowed fields

Request-boundary events 29001–29004 contain only:

- the fixed event name and numeric event ID;
- a normalized, fixed-set HTTP method (unknown method tokens become `OTHER`);
- the application-owned route template, never the raw URL;
- the response status code;
- whether the request had an authenticated principal;
- the server-generated `X-FullWorth-Request-Id` correlation value.

High-risk action events are deliberately narrower. Event 29011 contains only the fixed event name plus one allowlisted administrative action name. Events 29012–29013 contain only the fixed event name plus a validated 128-bit lowercase-hex server request ID; an invalid request ID is replaced with `<unavailable>` rather than logged verbatim. Event 29014 contains only the fixed provider name `plaid` plus one allowlisted operation name: `accounts_sync` or `transactions_sync`. It does not log the Plaid error code/type, user ID, connection/item/account identifiers, institution data, token material, request/response body, or provider request ID.

The event intentionally excludes raw paths, query strings, request/response bodies, email addresses, user IDs, provider IDs, IP addresses, claims, cookies, authorization headers, tokens, statement content, and financial values. The request ID is generated by FullWorth and ignores a client-supplied value.

Event 29004 is deliberately a probe signal, not proof that a caller supplied
another user's identifier. The same 404 can result from a genuinely missing
resource. FullWorth does not perform a second cross-owner existence lookup,
because doing so would expand data access and create a stronger oracle. The
event is emitted only for an authenticated request and one of fourteen fixed
method/route templates; it contains the template, never the supplied identifier.

These events complement persisted admin audit records. They do not replace the admin mutation audit trail and are not persisted in the application database. Administrative security events are emitted only after the corresponding audited mutation has been persisted; transactional staff-role changes are logged only after the surrounding database transaction commits. Idempotent role/access-key operations that make no persisted change do not create a second mutation event.

## Bounded repeated-event alerts

The request-boundary in-process aggregator groups only by the fixed event name, normalized HTTP method, application-owned route template, and authentication state. It never groups by or copies a user, IP address, raw URL, request ID, credential, statement, or financial value.

A five-minute fixed window emits these alerts:

| Alert ID | Name | Threshold |
| --- | --- | --- |
| 29101 | `repeated_authentication_rejections` | 25 matching 401 events |
| 29102 | `repeated_authorization_denials` | 10 matching 403 events |
| 29103 | `repeated_rate_limit_rejections` | 5 matching 429 events |
| 29104 | `security_event_aggregation_capacity_reached` | 5 events routed to the overflow bucket |
| 29105 | `repeated_ownership_scoped_resource_misses` | 20 matching ownership-scoped 404 events |

Each request-boundary aggregation key can emit at most once every 15 minutes. Threshold crossings during that cooldown are suppressed and reported as a count on the next emitted alert. Request-boundary aggregation memory is capped at 512 buckets, including a reserved overflow bucket. Buckets inactive for 20 minutes are removed before admitting a new key. If the cap is still full, new dimensions go to the fixed overflow bucket rather than allocating more state.

High-risk action detection uses the same five-minute window and fifteen-minute per-key cooldown, with only twelve possible allowlisted keys: eight administrative action names, the application-wide export and deletion scopes, and two provider operation names.

| Alert ID | Name | Threshold and safe grouping |
| --- | --- | --- |
| 29111 | `repeated_admin_mutations` | 5 events for one allowlisted administrative action |
| 29112 | `repeated_account_exports` | 10 application-wide export events |
| 29113 | `repeated_account_deletions` | 3 application-wide deletion events |
| 29114 | `repeated_financial_provider_attention` | 5 events for one allowlisted provider operation |

Unknown action, scope, or operation values are rejected before aggregation state is allocated. High-risk alerts never contain the source event's request ID, an actor or account identifier, Plaid data, or other user-controlled text. Alerts contain only the fixed event/alert names, the allowlisted dimension name and value, threshold, window length, and number of suppressed threshold crossings.

This aggregation is process-local and resets on API restart. In a future multi-instance deployment, the collector must combine `FullWorth.SecurityAlerts` across instances; the current production rule remains one API instance because startup migration ownership has not been redesigned.

## Operations

Route `FullWorth.SecurityEvents` to the security event stream and `FullWorth.SecurityAlerts` to the alert collector. Notification rules must use alert IDs 29101–29105 and 29111–29114 rather than parsing message text. Page or notify from the bounded alert stream, not from every individual event. Treat thresholds as initial operational defaults and tune the collector notification policy from observed safe alert volume; do not add user or financial dimensions to reduce false positives.

A capacity alert means the safe aggregation-key budget was exhausted. Investigate whether route cardinality changed or an unexpected endpoint pattern entered the pipeline; do not raise the cap until the source is understood.

An ownership-miss alert is an application-wide signal grouped by method, route
template, and authentication state. Triage for scanning or repeated stale client
behavior, but do not describe it as a confirmed cross-user access attempt without
separate evidence. Never add resource or user identifiers to the alert key.

Correlation through an individual event's request ID may be used to find nearby application diagnostics, but operators must not add secrets or user financial evidence to either stream.
