# Security event telemetry

FullWorth emits a dedicated structured log category, `FullWorth.SecurityEvents`, for request-boundary security outcomes that operators need to detect separately from debug and application logs.

## Events

| Event ID | Name | Trigger |
| --- | --- | --- |
| 29001 | `authentication_rejected` | HTTP 401 |
| 29002 | `authorization_denied` | HTTP 403 |
| 29003 | `rate_limit_rejected` | HTTP 429 |

The middleware surrounds rate limiting, authorization, and endpoint execution, so rejected requests are observed even when a downstream component short-circuits the pipeline.

## Allowed fields

Each event contains only:

- the fixed event name and numeric event ID;
- a normalized, fixed-set HTTP method (unknown method tokens become `OTHER`);
- the application-owned route template, never the raw URL;
- the response status code;
- whether the request had an authenticated principal;
- the server-generated `X-FullWorth-Request-Id` correlation value.

The event intentionally excludes raw paths, query strings, request/response bodies, email addresses, user IDs, provider IDs, IP addresses, claims, cookies, authorization headers, tokens, statement content, and financial values. The request ID is generated by FullWorth and ignores a client-supplied value.

These events complement persisted admin audit records. They do not replace the admin mutation audit trail and are not persisted in the application database.

## Operations

Route `FullWorth.SecurityEvents` to the security log stream in the deployment's log collector. Alerting and retention must operate on the fixed event IDs and names, not free-form message parsing. Until a bounded aggregation rule is deployed, do not page on every individual event; ordinary invalid credentials and expired sessions can produce isolated 401 responses.

Correlation through the request ID may be used to find nearby application diagnostics, but operators must not add secrets or user financial evidence to either stream.
